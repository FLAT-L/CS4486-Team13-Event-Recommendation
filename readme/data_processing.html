Data Cleaning and Feature Construction

Project Story: Two Stages

Stage 1 — Modernize and simplify (01 → 02 → 05). Reproduce the historical seventh-place method, replace its model and elaborate preprocessing with XGBoost and a simpler feature pipeline, then apply focused semantic cleaning to establish a strong reference.

Stage 2 — Extract useful evidence from underused data (09 → 15). After extensive experiments with additional processing and pretrained representations, investigate whether friends’ event histories provide information beyond the existing inputs. Compare positive histories with explicit negative histories.

Model lineage: Models 09 and 15 retain Model 02’s original features. Model 05 is the strong comparison reference; its cleaning is not inherited by 09 or 15.

Data cleaning, table joins and feature construction for the eight delivered models. Each model reads the six competition tables in models/data/raw.

2. Stage 1: Model 02’s simpler feature pipeline

Model 02 replaces the historical cluster-profile and location-reconstruction pipeline with direct metadata, content counts and social statistics. It does not need historical event clustering or geographic voting. These 142 features form the common input foundation for Models 05, 09 and 15.

Table joins and missing values

Users and candidate events are left-aligned to candidate rows. Events are scanned in chunks of 50,000 rows, retaining candidate IDs. Numeric conversion uses coercion to missing values. Missing profile rows remain in the dataset. User-profile and event-profile availability indicators record join coverage.

Categorical encoding

Five categorical columns use dense one-hot encoding fitted only on the training portion of each fold. Categories occurring fewer than 10 times are pooled. Unknown validation or test categories are ignored. Numeric features become float32; the dense representation distinguishes real zero from missing. Encoded width can differ across folds.

3. Stage 1: Model 05’s focused cleaning

Model 05 adds a small set of explicit validity and text-normalization rules to the simpler XGBoost pipeline. This completes the modernization stage and provides the strong reference for evaluating additional information.

Start with the complete Model 02 feature table. Preserve every candidate row and all 142 original columns. Add one tenure-validity indicator.

StepExact rule
Non-finite numeric valuesReplace positive and negative infinity with missing values.
Semantic boundsKeep age in [0,120], latitude in [-90,90], longitude in [-180,180] and timezone in [-720,840]. Values outside these ranges become missing.
Negative tenureAdd tenure_invalid = 1 for negative tenure and 0 otherwise. Replace negative tenure_days with missing values. Negative lead_hours remain available.

Location matchingNormalize the raw user location identically. Replace substring matches with whole-phrase matches bounded by non-word characters. Missing regions or user locations remain missing.
EncodingUse the same fold-specific dense one-hot encoder as Model 02.

4. Stage 2: Models 09 and 15 use friends’ event histories

This stage expands evidence beyond each candidate event. It retrieves event metadata through friends’ response histories, including records outside the labeled candidate set. Positive and negative profiles use the same fields and aggregation method; the response source changes from yes to no.

Exact Definitions: Positive and Negative Friend Profiles

Positive friend profile (Model 09): for each friend of the target user, average the 104 event fields over events where that friend appears in event_attendees.yes. Then average these friend-level profiles equally.

Negative friend profile (Model 15): for each friend of the target user, average the same 104 event fields over events where that friend appears in event_attendees.no. Then average these friend-level profiles equally.

“Positive” and “negative” refer to friends’ recorded event responses, not to two types of friends. No recorded response does not count as a negative response.

Both profiles use the same deduplicated friend set, excluding the target user. The 104 fields are start_time, lat, lng, c_1 through c_100, and c_other. Both averaging stages operate separately for each field using available values; friends without a valid value for that field are omitted, and a field remains missing if no friend contributes. The candidate event is retained when present in a friend’s response history. The same friend can contribute to both profile types through different events; records follow the source status lists without forcing them to be mutually exclusive.

Both models retain all 142 Model 02 features unchanged and append 104 fields, giving 246 input columns before one-hot encoding. They do not apply Model 05 cleaning.

  1. Read the target users’ deduplicated friend sets and exclude self-links.
  2. Select response records involving those friends, using yes for Model 09 and no for Model 15.
  3. Join the selected events to their metadata. Skip events whose metadata is unavailable.
  4. Convert invalid numeric values to missing. For each friend and each field, average only events with a valid value for that field.
  5. For each target user and each field, average the available friend means equally. A highly active friend does not receive greater weight.
  6. Leave a field missing when no friend supplies a valid value. Repeat the resulting profile across that user’s candidate rows.

The current candidate event is retained if it appears in a friend’s recorded history. An absent response is not treated as a no response. The source tables are static relationship snapshots.

5. Historical reference: Model 01 preprocessing

Model 01 reconstructs the seventh-place public approach. It builds 35 historical features and supplies separate feature subsets to a random forest and logistic regression.

Multi-scale event clustering

Read all 101 raw content counts as float32. Fit three MiniBatchKMeans models with 8, 20 and 40 clusters, batch_size 100, n_init 3 and random_state 42. Feed consecutive blocks of 10,000 events through partial_fit, retaining the historical behavior that excludes the final incomplete block from fitting. Assign cluster labels to every event afterward. Counts are not standardized or logarithmically transformed for clustering.

Historical profiles

Positive history combines yes and maybe responses and events created by the person. Negative history uses no responses; invitation history uses invited responses. User-event histories are binary after deduplication. Construct normalized cluster-frequency profiles for the user’s positive, negative and invitation histories, and friends’ positive and negative histories. Friends’ historical events are pooled as sets. Content prototypes pool the user’s and friends’ positive events, sum raw counts, and normalize the total. This historical profile construction differs from the two-stage friend means used by Models 09 and 15.

Location reconstruction

Build a geographic dictionary from event city, country and state fields. Correct the historical Congo country-name spelling. Index coordinates using integer five-times-latitude and five-times-longitude grid cells. Try the same grid cell first; otherwise inspect the historical neighboring-cell offsets from -10 to 10 in increments of two and use the nearest eligible cell. Fall back to the event’s recorded region.

Parse user locations using the historical double-space tokenization, country/city dictionary and US, Canadian and Australian region constants. Retain recognized locations. For unresolved users, combine votes from positive event histories and friends’ initially known locations. Keep similarly supported candidates until the adjacent vote counts show the historical fourfold drop. Friend voting uses a frozen initial location map.

Candidate features and row handling

Keep the first training record for each user-event pair, yielding 15,220 pairs. Use the same user folds as the other models. Candidate features include event and friend response counts, response ratios, geographic match, event-history similarity, multi-scale profile match, time until the event, creator friendship and content similarity. Feature extraction preserves the historical 35-column order. The final RF and logistic-regression masks omit age/gender and unused legacy fields.

Event-to-event participant similarity uses yes responses plus creators, excludes the target user from the shared-participant numerator, and divides by the smaller participant-set size. Historical positive profiles also include maybe responses. Historical event counts retain the original author semantics; they do not inherit Model 02’s target-user subtraction.

7. Exact Input Dictionary

One training row = one user–event candidate. IDs join tables and define folds; they are not model inputs. Numeric columns come first; one-hot columns follow. All XGBoost inputs are float32. Missing numeric values remain NaN.

What reaches the model when data is missing?

Input caseValue in the XGBoost matrix
Missing numeric metadataNaN. Missing profile rows are retained. The separate user_missing and event_missing flags indicate whether the entire joined row was absent.
Invalid numeric value in Model 05Infinity, out-of-range age, coordinates or timezone, and negative tenure become NaN. Negative tenure also sets tenure_invalid to 1.
Friend response countA known empty intersection gives 0. An unavailable friend or event response row gives NaN for the intersection count.
Friend profile in 09 or 15Omit missing values separately for each field at both averaging steps. If no friend supplies that field, its input is NaN. If no friend supplies any field, all 104 profile inputs are NaN and the original 142 inputs still enter the model.

The five categorical inputs: exact encoding

Field order is user_locale, user_gender, event_city, event_state, event_country. Fit one encoder on that fold’s training rows. A retained category produces one column: 1 for that category, 0 otherwise. Categories occurring fewer than 10 times share an infrequent column. A category never seen during fitting produces zeros for that field. __missing__ is an ordinary category subject to the same frequency rule. The five content groups come from balanced clustering on log-count correlations, with 20 fields per group. Each token sums its field embeddings and divides by the square root of its field count.

03. Look up each candidate event, encode it with all tokens visible, then flatten the final block in token order. Columns pretrained_t00_r000 through pretrained_t09_r127 are the 10 × 128 activations before final normalization. Append these numeric columns to the 142 inputs of 02. All 13,418 distinct candidate events matched the catalog.

04. Start from the same 137 numeric and five categorical fields as 02. Fit preprocessing on the outer training rows. Replace nonfinite numerics with the training median (fallback zero), apply a normal quantile transform with up to 1,000 quantiles, then append one binary flag per numeric field with training-fold missingness. Each transformed number, flag and category gets its own token, plus CLS. Category code 0 means missing, 1 means rare or unseen, and levels observed at least five times have their own codes.

06. Apply the frozen 03 encoder and a trained 64-unit SiLU encoder to each candidate. dense64_00 through dense64_63 are those activations in output-unit order. Append them to the original 142 inputs to form 206 columns. The decoder is used only during reconstruction.
